# Research notes — 2026-09-30

Review of `design-brief.md` before starting implementation. Part 1 is what was verified by hand against git 2.55.0 on this machine; part 2 is what the web research turned up about the libraries and editor bases; part 3 is the resulting recommendations and the decisions the brief asked to settle.

## 1. The core primitive, verified empirically

The brief's loop (worktree, amend, `rebase --onto`, update ref, remove worktree) works, but git 2.38+ has in-memory equivalents for the rewrite itself, and a rebase that checks out every pick is the slow part: 20 commits in 2.4 s in a worktree versus 64 ms in memory on godot. (A first draft of these notes claimed "40–400×" against a fresh checkout; the review pointed out that a persistent worktree switches between stack commits in ~15 ms, so the checkout cost was the wrong baseline. Section 3.6 uses one.) Everything below was run against a scratch repo and against a `--shared` clone of the local godot checkout (85,678 commits, 14,162 files at HEAD).

### 1.1 Editing a commit without a worktree

Trees can be built from blobs with a throwaway index file, so an amend never needs a checkout:

```sh
export GIT_INDEX_FILE=/tmp/suonetar-idx
git read-tree <commit-N>
new_blob=$(edited_content | git hash-object -w --stdin)
git update-index --cacheinfo <mode from ls-tree>,$new_blob,path/to/file   # never hardcode 100644: it strips +x and turns symlinks into files
new_tree=$(git write-tree)
new_N=$(git commit-tree $new_tree -p <parent-of-N> -F <original-message>)
```

Measured on godot: amend one file in commit 10 of a 20-commit stack and replay the 9 above it — **47 ms total**. Reading 200 blobs through `git cat-file --batch` took 63 ms, and `git diff-tree -p` of one commit took 2 ms. Scrubbing should therefore be pure object-database reads; a worktree is only for the cases where the user wants to *run* something (tests, a build) against commit N, and can be materialised lazily and kept out of the hot path.

### 1.2 Restacking: `git merge-tree --write-tree --merge-base`

`git merge-tree --write-tree --merge-base=<parent-of-C> <new-parent> <C>` is an in-memory cherry-pick of C onto the new parent. Verified behaviour:

- **Clean case:** prints the new tree OID, exit 0. Handles adds and deletes; detected a rename in the amended commit and carried the descendant's edit into the renamed file.
- **Content conflict:** exit 1, prints the tree OID, then one line per conflicted stage (`<mode> <oid> <stage>\t<path>`, stages 1/2/3 = base/ours/theirs), then messages. The written tree contains the file **with conflict markers**, honouring `merge.conflictstyle` (the global config here is `zdiff3`, and the output was zdiff3-style; overriding with `-c merge.conflictstyle=merge` produced plain markers).
- **Modify/delete conflict:** exit 1, stages 1 and 2 only, and the modified version is left in the tree.
- **Empty result:** if the amended parent already contains C's change, the output tree equals the parent's tree. The tool has to decide drop-vs-keep itself (`git replay` drops such commits silently).
- `-z` gives NUL-separated output with a structured message section (`<n>\0<paths…>\0<type>\0<message>`), `--name-only` drops modes/OIDs, `--no-messages` drops the messages.
- **Does not consult or record rerere.**
- **Merge drivers from `.gitattributes` are read from the checked-out worktree only**, not from the trees being merged (and in a bare repo not at all). Pass `git --attr-source=<tree> merge-tree …` so the attributes of the commit being replayed are used; this was verified by the research agent against 2.55, including a `BUG:` abort when combining `merge.renormalize=true` with a bare repo.
- `--quiet` (2.50) returns the exit status without writing most objects, useful for a "would this conflict?" preview. `--stdin` batches several merges in one process but inverts the status convention (0 = conflicted) and cannot be combined with `--merge-base`.
- The man page's "mistakes to avoid" section applies: an empty conflict list does not mean clean (check the exit code); mode, binary, file/directory, and rename/rename conflicts are not expressible as markers and show up only as stage entries; read conflicted content from the result tree's blob (it carries the labels) rather than re-merging the stage OIDs.
- **Does not touch the index or worktree at all**: with a stale `index.lock` sitting in the main worktree (simulating Claude Code mid-commit), `merge-tree`, `commit-tree`, `update-ref`, and `replay` all succeeded while a normal `git commit` correctly failed.

Timing on godot: one cherry-pick via `merge-tree` was **3 ms**; a shell loop of 20 sequential `merge-tree` + `commit-tree` spawns was **64 ms**. The equivalent traditional path (`worktree add` + `rebase --onto` of the same 20 commits) took **2.4 s**, of which 1.7 s was the checkout.

### 1.3 `git replay` — usable for the clean path, useless for conflicts

`git replay` replays a range in memory. Two things the brief should know that are not in older docs:

- **As of 2.55 it updates refs by default**, in an atomic transaction, and `--onto` updates *every branch in the range* like `rebase --update-refs`. The old print-only behaviour is now `--ref-action=print` (or `replay.refAction=print`). The first experiment here moved `main` without meaning to. Always pass `--ref-action=print`.
- `--contained` also updates other branches that point into the range (verified: a `feat-mid` branch pointing at commit 2 of 3 was rewritten alongside `main`).
- **On any conflict it exits 1 and prints nothing** — no tree, no indication of which commit conflicted. Still marked EXPERIMENTAL in the man page. So replay is a convenience for the all-clean case only; record-and-continue must drive `merge-tree` per commit.
- Replay of 20 commits on godot: **6 ms**.
- **Hazard:** with the default ref action, replay moves a branch even when it is checked out in a worktree, leaving that worktree's index and files stale. `git rebase --update-refs` deliberately skips such branches. See 1.6, which applies to the tool's own ref updates as well.
- Git 2.56 (released 2026-09-28) adds `--linearize` to drop merges. Upstream has an open request to make replay report conflict details the way `merge-tree` does; nothing has landed.

Git 2.54–2.56 also added an experimental **`git history`** command (`reword`, `split`, `fixup`, `drop`) built on replay: worktree-free, no hooks, rewrites descendant branches by default, and "does not support operations that can result in merge conflicts, by design". It is git's own first step into this space. `git history fixup` in particular overlaps with `git absorb --and-rebase`, and the tool's message-editing path could reuse `reword`. Same hazard as replay: it moves checked-out branches and copies no notes.

### 1.4 Ref updates, atomicity, and coexistence with Claude Code

- `git update-ref <ref> <new> <old>` is a compare-and-swap: with a stale `<old>` it fails with "cannot lock ref … is at X but expected Y". This is half of the coexistence story (the other half is the worktree update in 1.6): read the stack, do all work in the object database, and CAS the branch at the end. If Claude Code moved the branch meanwhile, the CAS fails and the tool re-replays onto the new tip (tens of ms) instead of clobbering anything.
- `git update-ref --stdin` with `start`/`prepare`/`commit` gives an **all-or-nothing transaction across refs**. Verified: a transaction updating `main` (CAS) plus creating a keep-alive ref either applied both or, with a stale CAS, applied neither. This is how every ref an operation moves should be moved together.
- All three local repos checked (suonetar, godot, scratch) use the `files` ref backend, so watching `.git/HEAD`, `.git/refs/heads/`, and `.git/packed-refs` with inotify is enough to notice Claude Code moving the branch. Reftable would need a different watch path; check `git rev-parse --show-ref-format` at startup.

### 1.5 Notes as tool metadata: what survives which rewrites

With `notes.rewriteRef=refs/notes/suonetar` set in the repo config, a note attached to a commit was **copied across `git rebase` and `git commit --amend`** (each run in a temporary worktree, as Claude Code would). It is **not** copied by `git cherry-pick`, `git replay`, or `git history` (`notes.rewrite.<command>` only supports `amend` and `rebase`; an earlier cherry-pick test here was a no-op pick and proved nothing), and will not be copied by the tool's own `merge-tree`/`commit-tree` path. The tool copies its own notes with `git notes copy --stdin`, which takes `<old> <new>` pairs and was verified to work. This mattered for a flag-the-conflict design that section 3 no longer proposes; it stays here as reference.

### 1.6 Moving the checked-out branch leaves the main worktree stale — the brief's loop has this gap too

The stack's tip is the branch checked out in the main worktree. After the tool (or `git replay`, or the brief's step 4 "update the branch ref") moves that branch, HEAD resolves to the new tip while the index and files still hold the old one. Verified: `git status` then reports the edit as a **staged change in the reverse direction** (`M  a.txt`, with the old content on disk). Claude Code would see, and could commit, a phantom revert of every edit made in the tool.

The fix is the two-tree update that `git checkout` performs when switching commits, run in the main worktree as the last step of the operation (a rebase, by contrast, holds the worktree for its whole run and switches it at every pick; this tool touches it once):

```sh
git -C <main-worktree> read-tree -m -u <old-tip> <new-tip>
```

Verified behaviour: it brings index and files to the new tip; **it refuses** (`Entry 'a.txt' not uptodate. Cannot merge.`, exit 128, nothing changed) when an uncommitted local edit touches a file that differs between the tips; it leaves uncommitted edits to other files alone; and it fails while `index.lock` is held, which just means retry shortly. So the tool's contract with the main worktree is one short, refusable, index-locked update per operation, never a sustained checkout. When it refuses, the right response is to tell the user which file Claude Code has in flight and stop, rather than stash on their behalf. Two things the review added: `update-index --refresh` must run first, or a mere `touch` of an unchanged file produces the same refusal; and the update and the ref move are two processes with a gap between them, which is not safe without holding a lock (3.2).

### 2.2 Prior art — GitButler's conflict representation, considered and set aside

**GitButler** (source inspected at master `6badede9`, 2026-09-30):

- License is still FSL-1.1-MIT; each released version becomes MIT two years after release. The `but` CLI is in the same repo under the same license.
- **Still takes over the working tree**: HEAD sits on a `gitbutler/workspace` merge commit, the index is rewritten to the union of applied branches, and hooks block `git commit`. A "single branch / normal git" mode exists behind a feature flag and is not default. Edit mode checks the commit out into the **main** worktree after stashing. So GitButler fails the coexistence constraint outright, and there is no "open commit N in an editor, then restack" command even in the CLI (an open issue proposes `but edit <commit>`).
- **Conflicted commit representation** (`crates/but-core/src/commit/mod.rs`, `crates/but-rebase/src/cherry_pick.rs`): the commit's root tree is the **auto-resolved** merge result, favouring "ours" = the new base, so the visible tree never contains conflict markers. Sidecar entries are upserted into that root tree: `.conflict-base-0`, `.conflict-side-0` (ours), `.conflict-side-1` (theirs), `.auto-resolution`, and a `.conflict-files` blob. The flag is a `[conflict] ` subject prefix plus a `GitButler-Conflict:` trailer (an extra commit header was the legacy form). Descendants of a conflicted commit are cherry-picked onto its auto-resolution tree, so conflicts do not cascade unless a descendant touches the same lines, in which case it becomes its own flagged commit.
- Rebase engine is gix-merge; `but-rebase` is `publish = false` and depends on the monorepo, so it is not reusable as a crate.

**jj**: the authoritative conflict data is an extra commit header `jj:trees` listing an odd number of tree OIDs; the git tree with `.jjconflict-base-N` / `.jjconflict-side-N` subtrees exists only to stop GC. Rebasing onto a conflicted commit is tree algebra (`new_base + (old − old_base)` with term cancellation), which is why jj conflicts can be resolved in a descendant. That algebra needs its own merged-tree type; it is not reproducible with plain git commands. GitButler's "auto-resolve to ours and re-merge each descendant" is the closest plain-git emulation, and it was the first draft's recommendation; the review showed it cascades and loses data in exactly the agent-stack shape this tool targets (3.1), so v1 does not record conflicted commits at all.

**Nothing else does the job.** Surveyed: lazygit (amend-any-commit via rebase, fixup helpers, custom patches — all through the main worktree), git-spice, git-stack, git-revise, StGit, Magit instant fixup, git-branchless `amend`/`restack`, GitHub's new `gh stack` (branch-level), revup, and the 2024–2026 Tauri GUIs graft and git-knife (metadata only). All of them either take over HEAD/worktree or are CLI-only with no editor round-trip. That validates building this rather than adopting.

**Sapling in `.git` mode** is officially supported with ISL, but index sharing with git is partial and it is out of scope by the brief's first constraint. Noted only for completeness.

### 2.3 Editor bases — the brief's ranking holds, with three updates

**CodeMirror 6** (MIT; view 6.43.13, 2026-09-22) remains the lightest full-featured base. What has changed since the brief:

- **Official LSP client**: `@codemirror/lsp-client` 6.3.0 gives completion, hover, diagnostics, go-to-definition, rename, signature help, and `formatDocument`. Transport is a three-method interface, trivial to bridge over a WebSocket or Tauri IPC. No code actions yet. This covers the "formatting" requirement for any language with a language server; for the rest, run an external formatter and dispatch a replace-all transaction.
- **Two-way merge view** in `@codemirror/merge` 6.12: side-by-side `MergeView` and single-editor `unifiedMergeView` with per-hunk accept/reject controls. The unified view against the parent commit is the scrub view, and its accept/reject controls are a hunk selector for free. **There is no 3-way merge view** in CodeMirror or in standalone Monaco (VS Code's merge editor is workbench-only, requests closed as not planned).
- Language coverage: 22 official Lezer grammars, 103 legacy stream modes, plus community packages. Adequate.
- The project moved from GitHub to a self-hosted Forgejo in April 2026; npm publishing continues normally.

**Tauri 2** (2.12.0, 2026-09-26) is fine, with one real Linux caveat: WebKitGTK 4.1 on NVIDIA/DMABUF has known blank-window and flicker problems that Tauri documents with environment-variable workarounds. Tauri 3 alphas add a Chromium (CEF) runtime and a GTK4/WebKitGTK 6 migration, but they are alphas. This is the argument for starting as a **localhost server plus browser tab**: same frontend, zero packaging, the user's own Chromium/Firefox, and a Tauri shell can be added later without rewriting anything.

**Others:** Monaco standalone (0.57, MIT, 2.4 MB core, native LSP since 0.55) is viable but heavier and has the same 3-way gap. Theia is a full Electron IDE build and disproportionate for one custom view. KTextEditor is the only native KDE-quality widget, but the diff viewer and formatter live in the Kate application rather than the framework, there are no Python bindings beyond a skeleton, and the only route is a C++ Kate plugin with a custom tool view. Neovim + diffview.nvim is possible but the stack panel would be a text-grid window. Zed, Lapce, and Helix extension APIs still cannot render custom UI; the rejections stand. GtkSourceView 5 from PyGObject is the one native option for a Python-based tool, at the cost of GTK4 in a KDE session.

## 3. Recommendations and decisions

Revised after the hostile review recorded in `hostile-review-2026-09-30.md`.

### 3.0 Review outcome

The reviewer reproduced the document's claims against git 2.55 and raised thirteen objections: three blocking, seven should-fix, three minor. All three blocking objections are accepted, and the first draft's central decision is reversed. Nothing was pushed back on for adjudication; the design questions the reviewer could not answer are listed in 3.11 for the author.

- **O1, apply step not atomic.** Reproduced: with `read-tree` first and the ref move second, a commit by Claude Code in the gap absorbs the user's edit into the wrong commit, and the prescribed revert then stages a phantom undo of it. Accepted; 3.2 now applies under git's own index lock with an intent record and pre-flight checks.
- **O2, auto-resolve recipe.** Replacing a conflicted path with its stage-2 blob drops the descendant's non-conflicting hunks in the same file; `merge-tree -X` does hunk-level resolution; directory/file conflicts leave `path~<sha>` entries in the written tree; favouring "ours" cascades conflicts through exactly the later-commit-refines-earlier-line shape that agent stacks have. Accepted; with O3 the engine has no auto-resolution at all.
- **O3, record-and-continue.** Trailers do not survive `rebase -i` squash (they land mid-message) or `commit --amend -m`; the flagged commit has two sources of truth; replaying a flagged commit is undefined; an auto-resolved tree is the silent leak, committed markers would have been the loud one. Accepted; v1 resolves before publishing. This was the elegant option chosen over the simple one, which the brief's last constraint says not to do.

### 3.1 Conflicts: resolve before publishing

The engine computes the entire replay in memory before touching any ref. If any commit conflicts, nothing is published. The conflicts are presented in stack order in the editor as part of the save; each resolution is fed back into the replay; when the whole stack is clean it is published once, atomically. Nothing halts in the repository (no rebase in progress, no detached HEAD, no flagged commits), so Claude Code keeps working throughout. This is the brief's "halt-and-prompt" with the halt moved out of the repo and into the tool's pending save.

- **Detection:** per-commit `merge-tree --write-tree -z --merge-base=C^ P′ C` with `--attr-source=<C's tree>`, exit code and stage list. The written tree with markers is shown in the resolve view, with readable labels instead of raw OIDs.
- **Resolve view (v1):** the conflict-marker file opens in the embedded editor with zdiff3 markers (already the author's `merge.conflictstyle`, so base and both sides are inline), marker-aware decorations, and take-ours / take-theirs per block. The four texts are labelled by meaning: base is the descendant's original parent, ours is the rewritten parent carrying the user's edit, theirs is the descendant. Base→ours is "what you changed" and base→theirs is "what the later commit did", which are the two intents that collided, so no default side is suggested.
- **Break-out:** "Open in mergetool" writes the four blobs into the persistent worktree and runs the configured `merge.tool` command with `$BASE`, `$LOCAL`, `$REMOTE`, `$MERGED` substituted, honouring `trustexitcode`, then reads the result back. The author's config points at Rider, whose three-pane-with-base merge view comes for free this way; KDiff3 and Meld work the same. An embedded 3-pane view is a later addition, built from `@codemirror/merge`'s diff primitives, if the markers grate.
- **Non-content conflicts** (modify/delete, directory/file, rename/rename, mode, binary): v1 offers an explicit per-type choice or refuses the save with a message. `-X ours|theirs` is available for hunk-level bulk resolution but is never applied silently.
- **Walking away mid-resolution:** v1 holds the pending save in memory; persisting it as `refs/suonetar/pending/<branch>` is a later addition if it turns out to be needed.
- Record-and-continue is revisited only if conflicts that must outlive a session actually occur.

### 3.2 Coexistence protocol

An operation is: read the stack, compute everything in the object database, then apply under git's own lock.

1. **Pre-flight.** HEAD must be a symbolic ref to the stack branch. Refuse if any of `rebase-merge/`, `rebase-apply/`, `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `BISECT_LOG`, or `sequencer/` exists for the main worktree (reproduced: moving the branch during Claude's `rebase -i` strands its `--continue`). Use `git worktree list --porcelain` to find branches checked out elsewhere; never move those.
2. **Lock.** Create `.git/index.lock` with `O_EXCL` and copy the index to a private file. Every git command that writes the index now fails with "File exists" instead of racing (reproduced). Write an intent record (`.git/suonetar/intent.json`: old tip, new tip, pid) so a crash mid-apply is recoverable on the next start.
3. **Apply.** With `GIT_INDEX_FILE=<private>`: `update-index -q --refresh` (so a `touch` of an unchanged file does not cause a refusal), then `read-tree -m -u <old> <new>`, then re-verify the branch still equals `<old>`, then the `update-ref --stdin` transaction with compare-and-swap. Install the private index by writing it to `index.lock` and renaming over `index`, git's own lockfile protocol. Remove the intent record.
4. **On refusal or CAS failure:** revert with the private index, which nothing else can have touched, release the lock, and report. On CAS failure re-read the stack and re-apply the edit through 3.3.
5. **Stale lock:** if `index.lock` already exists, report its age and stop rather than retry forever; a git process killed by an agent's command timeout leaves one behind.

What the lock does not cover, stated plainly: Claude Code's direct file writes (its Edit and Write tools, `sed -i`, formatters) are invisible to git locks, and a Bash-driven write after the tool's update can silently revert it because it does not re-read the file. The refresh-then-`read-tree` sequence catches a write to an affected file only if it lands before the refresh. The remaining hole can be closed cooperatively: a PreToolUse/PostToolUse hook pair in Claude Code sharing an atomic mutex with the tool (`mkdir .git/suonetar/lock`) so the tool applies only between Claude's tool calls. Whether to adopt that is an author decision (3.11); the lock-based protocol is self-contained and comes first either way.

Also from the review: `read-tree -u` overwrites an ignored file that the new tip starts tracking, as `checkout` would, so the pre-flight refuses if any path the update would write is currently an ignored untracked file (`git ls-files -o -i --exclude-standard` against the changed paths); gitlink changes are refused in v1 rather than passing `--recurse-submodules`; and paths with a `filter=` attribute (LFS, git-crypt) are refused for editing, because `hash-object --stdin` bypasses clean filters and would commit a pointer or plaintext.

### 3.3 Edit identity across the other process's rewrites

An edit is keyed by SHA only for an instant. Claude Code amends, rebases onto `main`, reorders, and squashes, and after any of those N has a new SHA or no longer exists. So an edit is stored as a patch (N's tree → edited tree) and applied to the matched commit N* by three-way merge (`merge-tree` with base N, ours N*, theirs the edited tree), which may itself conflict and then goes through 3.1. Matching uses author identity plus author date, which `amend`, `rebase`, and `cherry-pick` preserve, with patch-id as a secondary key; the UI confirms any inexact match. An editor buffer bound to a commit and path detects that its commit vanished and says so rather than saving into the void.

### 3.4 Undo

Undo of "edit N" is another edit: restore the previous tree of the touched paths at the matched commit and restack through the normal path. It works after Claude Code has committed more on top, which a compare-and-swap back to old values does not. History lives in the branch reflog, written with `update-ref -m "suonetar: <op>"`; reflog entries keep the old commits alive for `gc.reflogExpireUnreachable`, which the tool sets to a year in the repo config on first use so nothing it ever replaced is pruned, and, unlike refs under `refs/suonetar/undo/`, do not show up as duplicate undecorated history in `git log --all --graph` (reproduced) or get pushed by `push --mirror`. No oplog file, no undo refs. Keep refs would only be needed for state that must outlive the reflog window, and v1 has none.

- **As built (plan 04).** Each reflog message names the tip it moved from (`suonetar: apply 3 commits from <old>`), so undo needs nothing but the reflog. When nothing has moved the branch since, undo moves it back to exactly the old commits through the locked publish, keeping SHAs and signatures, and pressing again redoes. When commits were made on top, undo writes drafts instead: each replaced commit's own change laid onto its replacement's parent as the apply made it, so only commits whose content or message the apply changed get one (every replacement must still be in the stack, or undo is unavailable), and the user reviews and applies them like any edit. If the undone apply's pre-commit hook reformatted files, the commits restacked above get formatting-revert drafts too, and the hook runs again on their Apply. Undo is one level deep: once an undo is the newest Suonetar entry, the button redoes, and older entries are reached by hand (`docs/recovery.md`).

### 3.5 Stack identity

- **Base is explicit.** `git config suonetar.base`, or a pick in the UI, defaulting to the newest merge-base among the default branch of `origin` and `upstream` (`refs/remotes/<remote>/HEAD`) and its local copy, `init.defaultBranch`, and `main`/`master`. Not `@{upstream}`: on a pushed feature branch that empties the stack after every push. Commits already reachable from a remote are shown as published, with the force-push implication, not hidden.
  - On the default branch itself (the author works directly on `dev`), its remote copy is the base, so the stack is the unpushed commits and empties after every push. Decided 2026-09-30: the author rarely force-pushes the shared default branch, and sets `suonetar.base` when they do.
  - Other remotes' HEADs are not candidates: since git 2.48 every fetched remote gets one, and a laptop or backup remote's HEAD can be a feature branch that already contains the tip, which would hide its unmerged commits.
- Working directly on `main` gives an empty stack, and a merge commit ends the stack; the UI says both.
- **v1 moves only the stack branch.** Other branches pointing into the range are reported as left behind, not rewritten: backup branches exist precisely so they are not moved, branches with their own commits forked from the stack cannot be moved correctly anyway, and branches checked out in linked worktrees must be skipped as `rebase --update-refs` does (verified).
- **Live follow** is a `rev-parse` poll once a second or on window focus. Re-reading before each operation is the correctness mechanism; inotify on ref files was YAGNI, and linked worktrees keep their HEADs elsewhere.

### 3.6 Editing model: edit inside the diff, drafts per commit

The author's answer to the editor question (3.11): one window, click between commits and the embedded editor changes, with changes mostly read linearly and often large. So the embedded editor is the primary surface from the start, and the "existing editor on a worktree" option is reduced to a right-click break-out.

- **The primary view is the per-commit diff, and it is editable.** CodeMirror's `unifiedMergeView` shows a file with its diff against the parent inline and lets the new side be edited: for commit N, the original is the file at N's parent and the document is the file at N. Reading Claude Code's stack and fixing what is wrong happen in the same view. Side-by-side `MergeView` is a toggle for wide diffs, with unchanged regions collapsed. Keyboard navigation across files, hunks, and commits.
- **Rejecting a hunk moves it down the stack.** After a hunk is rejected in N, N no longer contains it but N+1's tree still does, so the replay of N+1 picks it up as part of N+1's change. Hunk moving needs no feature of its own.
- **Drafts are per commit.** An edited buffer is hashed to a blob and recorded as a draft against its commit (blob OIDs in `.git/suonetar/drafts.json`, the blobs themselves in the object database, so a crash loses nothing). Switching commits is free; the draft badge stays on N. **Apply** publishes every draft in stack order in one replay; a draft on N3 made before N1's edit propagated is applied as a patch onto the rewritten N3 through the edit-as-patch path (3.3).
- **The persistent worktree is a materialisation, not the editing surface.** A detached worktree under `.git/suonetar/wt/` holds the selected commit plus its draft (the reviewer measured 11–16 ms per switch on a synthetic 15,000-file repo). It is the working directory for formatters, the place pre-commit hooks run at publish (3.7), the target of "run tests at N", and the path handed to the right-click break-out that opens a file in the user's own editor.
- **Formatting in v1** is an external command on the buffer (`rustfmt --emit stdout`, `ruff format -`, `prettier --stdin-filepath`) run with the worktree as cwd so config resolution works. LSP through `@codemirror/lsp-client` against the worktree is later.
- **Scrubbing** stays pure object-database reads; the worktree switch happens lazily when something needs files on disk.

### 3.7 Commit-writing correctness, required in the MVP

- File modes from `ls-tree`; symlinks, gitlinks, and binaries (a `-` in `diff-tree --numstat`) are not opened in the editor.
- Author name, email, and date preserved through `GIT_AUTHOR_*`; committer is now; the `encoding` header is kept; message bytes pass through untouched.
- `commit.gpgSign` is read and `-S` passed explicitly, because `commit-tree` ignores the config (verified by the reviewer: it wrote an unsigned commit where `git commit` failed). Expect one pinentry prompt per replayed commit.
- Empty commits are kept and shown as empty.
- Commit-message editing is in the MVP: it is the same write path and about twenty lines.
- **Pre-commit hooks run lazily, at publish.** The author's target repo uses them and is fine with evaluation "once it flushes to the main repo". For each rewritten commit in stack order: materialise it in the persistent worktree, stage its changes against its new parent, and `git hook run pre-commit` there (which honours `core.hooksPath`). If the hook rewrites files, fold the result into that commit's tree and replay the descendants onto the reformatted tree. If it rejects, treat it exactly like a conflict: show the output, let the user fix that commit, retry. Conflicts and hook failures are one loop, "this commit needs attention before publish", and nothing is published until every commit passes. Cost is one worktree switch plus one hook run per rewritten commit; a knob to run only the edited commits and the tip exists if that turns out slow. `commit-msg` and `post-rewrite` are not run, as with `replay` and `history`.

### 3.8 Stack

**TypeScript end to end, in Electron.** Decided 2026-09-30 after the language discussion recorded in 3.11.

- **Why one language.** The frontend is TypeScript because CodeMirror is a DOM library, and CodeMirror is the choice because it is the only lightweight open-source editor that ships the editable diff and merge views this tool is built around. Once that is fixed, the least total complexity is the engine in the same language: one toolchain, shared types across the process boundary, `child_process` for git. Python would have made it two languages for no gain; Rust plus Tauri was a close second with a better shell and a worse build, and was set aside because the preference for Rust was the only argument for it.
- **Why Electron.** The author vetoed a localhost server with a browser window. With a TypeScript engine, Electron is the remaining one-language shell: the engine runs in the main process, CodeMirror in the renderer, and the two talk over typed IPC (`contextBridge` plus `ipcRenderer.invoke`, with the request and response types shared). No server, so the localhost security concerns the review raised do not arise. The costs are a large install and bundled Chromium; the benefits are no WebKitGTK, no window-management hacks, and native Wayland via Ozone.
- **Engine shape.** Shell out to the system git through one injected runner function so the engine is testable without a UI; a persistent `git cat-file --batch` child for blob reads; `-z` output everywhere it exists.
- **UI.** Plain TypeScript with Vite and the CodeMirror packages (`@codemirror/merge` for the editable diff views). Svelte 5 is adopted only if the panel's state handling gets messy without it; the toolchain is smaller without it.
- **Testing.** Vitest with real-git integration tests over generated repositories, not mocks. The runner seam earns its place by letting a test inject "the other process" between the tool's git calls, which is how the concurrency protocol gets exercised.
- **Standards.** `CLAUDE-typescript.md` renders the general standards for TypeScript and is imported by `CLAUDE.md`.

### 3.9 Corrections to the brief

- The core primitive is not the worktree/`rebase --onto` loop: the rewrite is in-memory `merge-tree` per commit, and a worktree is an editing context, not a rewrite mechanism.
- The brief's step 4, "update the branch ref", leaves the main checkout stale with phantom staged changes (1.6), and updating it is not safe without a lock (3.2).
- "Don't take over the main working tree" cannot mean "never touch it"; it means no persistent checkout, no HEAD games, no hooks in the repo, one locked update per operation, and refusal rather than stashing when the other process has edits in flight.
- The conflict decision goes the other way from the brief's lean: resolve-before-publish, not record-and-continue.
- `git replay` moves refs by default since 2.55 and is silent on conflicts; not a building block.
- git-branchless and scm-record come off the dependency list.

### 3.10 Build order

Each slice is usable on its own; the engine needs no editor to be de-risked.

1. **Engine (TypeScript in Electron's main process, shell-out to git) with integration tests:** stack discovery with explicit base and published-commit marking; commit, file, and diff reads; in-memory amend and replay with conflict detection; edit-as-patch with author-identity matching; locked apply with pre-flight, intent record, and CAS; reflog undo; the correctness list in 3.7. Tests include the interleaved-other-process cases from the review (commit in the gap, rebase in progress, touched-but-unchanged file, branch checked out in a linked worktree, ignored file in the way). A throwaway CLI that opens a blob in `$EDITOR` serves as the manual smoke harness.
2. **Read-only scrubbing UI:** commit list with published and left-behind markers, per-commit file list, inline and side-by-side diff against the parent, keyboard navigation across files, hunks, and commits. Useful by itself for reading Claude Code's stacks. This is where the UI work concentrates.
3. **Editing:** drafts per commit, Apply, hunk reject, message editing.
4. **Publish loop:** in-editor conflict resolution with the mergetool break-out, pre-commit hooks at publish, undo.
5. **Later:** LSP against the worktree, embedded 3-pane merge view, pending-save persistence, optional Claude Code hook coordination.
   - Formatting in the editor (3.6): deferred by the author on 2026-09-30, since the target repository's hook lints but does not format and no formatter is chosen yet. An external command run on the file in the private worktree at that commit would cover stdin and in-place formatters alike.
   - A list-then-fetch `commitDocument`: measured unnecessary for now, since the target repository's largest recent commit is 59 files and under 800 KiB in total.
   - An application icon, for the window and the desktop launcher (asked for by the author on 2026-09-30).

### 3.11 Decisions for the author

Answered 2026-09-30:

- **Concurrency:** the author does not edit the stack while Claude Code is working, but nothing may be lost whatever it does. The locked apply, refusal instead of stashing, edit-as-patch, the year-long reflog expiry, and the ignored-file pre-check are the guarantees; the Claude Code hook pair stays optional and deferred.
- **Editor:** embedded, one window, click between commits and the editor changes; the existing editor is a right-click break-out only. Section 3.6 is built around this; the "Kate on a worktree first" phase was dropped as throwaway.
- **Conflict default side:** dissolved. The resolve view shows base and both intents (3.1).
- **Pre-commit hooks:** the target repo uses them; lazy evaluation at publish is acceptable (3.7).
- **Language and shell:** TypeScript end to end in Electron (3.8). The author dislikes both TypeScript and Python but chose the simplest system over a preferred language; the localhost-server-plus-browser-window option was vetoed outright.

- **Editable scope:** every commit in the stack, with already-pushed ones marked. Claude Code works in the main worktree only for now; anything checked out elsewhere or forked from the stack is skipped and reported.
- **Repo features:** nothing fancy. Do what is safe and easy: pass `-S` when `commit.gpgSign` is set, refuse to edit paths with a `filter=` attribute, refuse gitlink changes. Complicated cases are handled when they come up.

No design questions remain open.
